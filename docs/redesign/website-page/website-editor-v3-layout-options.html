Website Editor v3 — shell-integration options DECIDED: Option B (+ collapsed NavRail) · frames are 1440×900 at true scale · chrome dimensions read from source Companion to website-editor-v3-gap-analysis.md

What was being decided

v3 is authored as a full-viewport application: #root{height:100dvh}, body{overflow:hidden}, its own 72 px navigation rail, and three independently-scrolling columns. The repo's authenticated shell has its own opinion — it owns the sidebar, the top bar, the breadcrumb trail, and a page gutter that guard:page-padding keeps single-sourced in PageContainer. Those two facts have to be reconciled before any of v3 gets built.

All three frames below render the same editor content — 340 px tool panel, canvas, 380 px inspector — so the only variable is the chrome around it.

Decided 2026-07-25: Option B, with one amendment — the collapsed NavRail (72 px) is reused inside the editor's own layout, so app navigation is not lost. B's remaining win over A is the 93 px of vertical chrome (top bar + breadcrumbs) it does not render, and not having to edit AppShell, which every authenticated page shares. Its cost is that a new route group must re-establish auth, community resolution, feature gating, the lapsed-community lockout and AppQueryProvider for itself. See website-editor-v3-gap-analysis.md §9.
The original recommendation was Option A, and the frames below still present all three as they were built for the decision. Keeping them is deliberate: the canvas-width table is the reason multi-page and the desktop preview behave the way they do, and it will be worth re-reading if the layout is ever revisited.

Canvas width is what is left after the tool panel (340) and the inspector (380). v3's desktop preview is authored at 1000 px (const width = {phone:400, tablet:760, desktop:1000} in editor-v3.jsx), so anything below that scales or scrolls.

What was actually chosen sits between A and B. B was decided with the collapsed NavRail reinstated, so it gives back the 72 px the “no shell” column above saves horizontally: canvas 648 px at 1440, 1128 px at 1920, 1768 px at 2560 — identical to Option A. The difference that survives is vertical: without the shell's top bar and breadcrumb strip the canvas gets 848 px of height instead of A's 755, and no shared shell file has to be edited. Read the B column above as “B as originally drawn”, and the A column as the width B actually ships with.

C's cap is max-w-[1400px] in PageContainer. Subtract the lg:px-10 gutter (40 px each side) and the two panels, and the canvas settles at 600 px on every monitor wider than about 1560 px. Widening the cap for one route would mean either a per-page override of the single-sourced gutter — the thing guard:page-padding exists to prevent — or raising it app-wide.

What each option costs

A — Full-bleed inside the shell

Original recommendation — not chosen

The app's real sidebar, top bar and breadcrumb trail stay. Below them the editor fills the viewport with no gutter and manages its own scrolling.

Shell change required
This is not possible today. AppShell renders <PageContainer> unconditionally around {children} (app-shell.tsx:232) and <main> is overflow-y-auto. Needs a full-bleed opt-out: skip PageContainer and switch <main> to overflow-hidden + min-h-0 for flagged routes. One prop or one route predicate — but it is a shell edit, and every authenticated page shares that file.
Guards
guard:page-padding scans (authenticated)/**/page.tsx for root px-*/py-* and page-level <main>. The editor adds neither, so a // page-padding:exempt is likely unnecessary — but the guard should be re-read when the opt-out lands rather than assumed.
Chrome stack
56 (top bar) + 37 (breadcrumbs) + 52 (v3's own bar) = 145 px before the canvas. v3's bar repeats the page title the breadcrumb already shows. Merging them — moving Preview/Publish and the save status into the shell's top bar, or dropping v3's bar and letting the breadcrumb strip carry the actions — recovers 52 px and removes the duplication. Worth doing.
Accessibility
The shell's single <main id="main-content"> stays the skip-link target, and it now contains three scroll regions — each needs a label and a reachable scroll container. Focus order stays sidebar → top bar → editor, which matches every other page.
Below 1024 px
Sidebar is already a drawer. v3's phone gate takes over under 768 px; 768–1023 px gets the editor with the inspector as an overlay panel, which v3 already models (overlay-panel + useMedia("(max-width:1279px)")).

B — Full-bleed, no app shell

Chosen — with the collapsed NavRail reinstated

The editor owns the entire viewport, with its own back affordance. Closest to the mockup, which draws its own nav rail.

Shell change required
A route outside the (authenticated) group's shell layout, or a shell bypass. Auth, community resolution, feature gating and the billing-lockout banners are all wired through that layout today, so each has to be re-established on the new route rather than inherited.
What is lost
  • Sidebar navigation — leaving the editor becomes a deliberate act.
  • Command palette (⌘K) entry point.
  • Breadcrumb trail, which is how the app answers “where am I”.
  • The subscription/free-access banner strip. That one matters: a lapsed community would sit in the editor with no indication.
What is gained
93 px of height over A, and no edit to AppShell — a file every authenticated page shares. The 72 px of width is given back by the decision to reinstate the collapsed NavRail, so the canvas ends up the same width as A.
Decision
Chosen, with the collapsed NavRail reused inside the editor's own layout — so the sidebar is not lost, only the top bar and breadcrumbs are. The accepted cost is that the new route group re-establishes auth, community resolution, feature gating, the lapsed-community lockout and AppQueryProvider for itself. Command palette and the billing banner strip are addressed separately (gap analysis §9, rows 2 and 4).

C — Standard page gutter

Not viable for a canvas editor

The editor renders as a card inside the normal padded, capped column — exactly like every other authenticated page.

Shell change required
None. No guard work, no exemption, no risk to other pages. This is its entire argument.
Why it fails
  • Canvas is capped at 600 px forever (see the table above) — 60% of the desktop preview it is supposed to show.
  • The editor's internal scroll regions fight the page scroll: <main> is overflow-y-auto, so a fixed-height editor either clips or the whole page scrolls and the tool panel scrolls away with it.
  • The sticky canvas bar and the inspector both assume a viewport-height column.
If chosen anyway
The panels have to shrink — roughly 280 px tools, 320 px inspector — and the design's resizable tool panel (280–560 px range) loses most of its range. The canvas becomes a scaled thumbnail rather than a preview, which undermines the reason to build a canvas editor at all.

One thing the frames deliberately do not show. v3 draws its own navigation rail (Rail() in editor-v3.jsx: pinnable, hover-expands to 248 px, overlays rather than pushes). That is a mockup stand-in for the sidebar the app already has, and it is close to — but not the same as — AppSidebar/NavRail (72 / 260 px, click-to-expand, persisted in a context provider). Options A and C render the real one. Shipping v3's rail would fork navigation for a single route; the behaviours worth keeping from it (hover-expand, overlay-instead-of-push) belong in NavRail for the whole app or nowhere.
