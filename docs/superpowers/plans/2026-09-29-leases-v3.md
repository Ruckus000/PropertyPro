# Leases v3 — implementation plan

**Source:** the Claude Design handoff "Leases page redesign", chosen direction
1a / Leases Roster v3. The prototype's audit and schema proposal were written
without the repo open. This plan corrects them against the code at `d043b0f`.
Decisions, billing options for the client, and open questions are in
`docs/superpowers/specs/2026-09-29-leases-v3-decisions.md`. Read that file
first.

**Shape:** three phases, each its own PR. Phase 1 is additive and ships with
no UI change, so production keeps working before Phase 2 exists.

## Premises checked against the code (the design got these wrong)

1. The proposal's `sql\`CHECK …\`` entries inside `pgTable` aren't valid
   Drizzle. They're `check(name, sql)`, and constraints on existing tables are
   added `NOT VALID`.
2. `users.id` is `auth.users.id`, so "make `users.email` nullable" is a
   platform change. It's replaced by `resident_contacts` behind a
   per-community switch (decisions §2).
3. Nothing generates `rent_obligations`, so there's no billing to keep
   consistent yet. Guard: a lease with unpaid obligations can't be cancelled,
   deleted or transferred (decisions D9).
4. The GET route's resident read filter is `residentId === actor`. With
   several residents per lease it must come from `lease_residents`, or
   co-tenants lose access (D7). This is a security-relevant change.
5. `logAuditEvent` already records every lease mutation, so the proposal's
   `lease_events` table is dropped (D3).
6. New leases must start on the 1st (`validateLeaseDateWindow`). Kept for now
   (D8, needs the client).
7. Move checklists are already created on lease create and on termination. The
   prototype showed them as confirmation messages only.
8. `units.rent_amount` is maintained by a trigger that fires only on lease
   writes. The rent of a future-dated renewal therefore reaches the unit late.
   This bug exists today and is out of scope; it's recorded in the decisions.

## Phase 1 — schema and API (EXPAND; no UI change)

**Migration class:** EXPAND. `0080_leases_v3_expand.sql` adds four tables, new
columns, one enum value and nullable `resident_id`, and back-fills
`lease_residents`. Nothing is dropped. Rollback: the new tables and columns are
unused by old code, so reverting the app deploy is enough; the migration can
stay.

**Before applying to production** (manually, per `AGENTS.md` §2), run these and
record the results in the PR:

```sql
-- D4: rows the NOT VALID checks would reject
SELECT count(*) FROM leases WHERE end_date IS NOT NULL AND end_date <= start_date;
SELECT count(*) FROM leases WHERE rent_amount < 0;
SELECT count(*) FROM leases WHERE rent_amount = 0;
-- rent_obligations drift (decisions §1)
SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint WHERE conrelid = 'rent_obligations'::regclass;
SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint WHERE conrelid = 'leases'::regclass;
```

If every count is 0, a follow-up migration runs `VALIDATE CONSTRAINT` on the
three. If `rent_amount = 0` rows exist, they need a `zero_rent_reason` from the
client before validation.

**P1-S2 lease domain rules (pure, no I/O)**
- `apps/web/src/lib/leases/lease-state.ts` and tests. Status is derived from
  dates and never stored:
  - Lease phase: `upcoming | current | moving_out | ended | cancelled`.
  - Unit status: `vacant | pre_leased | leased | expiring | holdover |
    month_to_month | moving_out | offline`.
  - Also: the §83.575 notice deadline, the §83.57 month-to-month notice check,
    the §83.49 notice-due date, and the end date for a term that clamps to
    month end (Aug 31 + 6 months = Feb 28).
- Done: `pnpm --filter @propertypro/web exec vitest run src/lib/leases`

**P1-S3 residents read path and lease writes** (`/api/v1/leases`)
- GET:
  - A non-admin sees a lease only through a current `lease_residents` row
    naming them. During dual-write, `resident_id` is kept as a fallback.
  - Every lease comes back with `residents[]` and the new fields.
  - For non-admins, `notes` and deposit details are redacted.
- POST accepts:
  - `residents[]` (user ids, contact ids, or a new contact when the community
    switch is on). The legacy `residentId` still works.
  - `zeroRentReason`/`zeroRentNote`, `noticeDays`, `deposit`,
    `idempotencyKey`.
  - Writes are dual: `resident_id` is set to the primary resident when that
    resident is a user.
- PATCH accepts `version` and returns 409 when it's stale. It also takes:
  - The move-out fields (`moveOutOn`, `endVia`, `endReason`,
    `noticeReceivedOn`).
  - `status: 'cancelled'` with `cancelledReason`, allowed only before the
    start date.
  - `signedDocumentId`, `noticeDays`, and the zero-rent fields.
- DELETE and cancel return 409 while the lease has unpaid obligations (D9).
- Files:
  - `apps/web/src/app/api/v1/leases/{route,contract}.ts`
  - `apps/web/src/lib/services/lease-service.ts`
  - `apps/web/src/lib/services/lease-expiration-service.ts`
  - `apps/web/__tests__/leases/leases-route.test.ts`
  - `apps/web/src/lib/services/export/table-registry.ts`
- Done:
  - `pnpm --filter @propertypro/web exec vitest run __tests__/leases`
  - A test proves a co-tenant sees the lease and a non-party doesn't.

**P1-S4 offers, deposits, contacts, transfer, offline units**
- `/api/v1/leases/offers`:
  - Send, respond, withdraw, resend after expiry, and sign.
  - Signing creates the renewal lease starting the day after the current one
    ends. The current lease row is not changed until then.
- `/api/v1/leases/deposits`: record, the E14 import path, and disposition.
- `/api/v1/leases/contacts`: returns 403 unless
  `leasesAllowResidentsWithoutEmail === true`.
- `/api/v1/leases/transfer`:
  - Ends the old lease (`end_via = 'transfer'`) and opens the new one.
  - Carries the deposit.
  - Refused while there are unpaid obligations.
- `/api/v1/units` PATCH: the offline fields.
- Every mutation takes `requirePermission(membership, 'units', 'write')`, is
  audit-logged, and is apartment-gated, the same chain as the existing route.
- Done: route tests for each, including cross-community ids rejected and a
  non-manager getting 403.

## Phase 2 — Leases page UI

Rebuild the v3 roster in repo components, working from the prototype's
behaviour, not its markup:
- Summary tiles that also filter.
- The table grouped by floor, collapsible, 50 rows at a time.
- The unit panel with residents, renewal stepper, deposit, documents and
  history.
- Dialogs: new or edit lease, renew/offer, end early or move out, cancel
  pre-lease, transfer, and put a unit offline.
- The alert-windows menu and undo from the confirmation message.

Constraints:
- Design tokens only. No slash-opacity (corpus: it renders nothing).
- `PageHeader` provides the `<h1>`, `PageBody` handles layout, and only the
  focus rings are coral.

Files: `apps/web/src/components/leases/*`, `apps/web/src/hooks/use-leases.ts`,
`apps/web/src/lib/utils/lease-utils.ts`, `apps/web/src/app/(authenticated)/dashboard/leases/page.tsx`.

Done:
- Component tests for the status mapping and each dialog's validation.
- `pnpm --filter @propertypro/web build`.
- One manual pass in a real browser at desktop width. This was never done on
  the prototype.

## Not in this project

- The rent generator and the billing options (decisions §1).
- Co-tenants leaving mid-lease (E5; the column is ready).
- Prepaid rent.
- Dropping `leases.resident_id`: a CONTRACT migration after Phase 2 has shipped
  and nothing reads the column.
